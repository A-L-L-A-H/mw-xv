## Initial CI service objectives (measurement targets, not guarantees)

- PR quick verification target: under 10 minutes wall-clock, measured over at least 10 representative affected runs. Not yet measured as a separate stable cohort.
- Full promotion suite target: under 20 minutes wall-clock, measured over at least 10 full runs. Ten successful full push runs are observed at 2.57–3.73 minutes (3.23-minute mean); see [M0.06 evidence](../roadmap/evidence/M0.06.md). This supports the current CI workflow budget only; it is not an application latency SLO.
- If targets are missed, report slow jobs and separate required gates; never omit PostgreSQL/browser/security merely to hit the target.
- Browser failure reports/traces/screenshots/video use explicit 7-day artifact retention in CI. Repository-level artifact/log retention is inherited (`artifact_and_log_retention_days` is unset in the repository API); actual log retention remains unverified.
- Scheduled reliability: GitHub schedules are best-effort; workflows must be manually runnable and M8.10 must find stale/missed runs.

Measure one workflow's wall-clock duration with `gh api repos/bjo163/moonwitness-xiv/actions/runs/RUN_ID --jq '[.run_started_at,.updated_at]'`; convert the timestamps to minutes. This includes queue time and is a conservative workflow-level budget, not a job-duration or app-latency benchmark.

Before calling these supported policy, confirm the chosen runtime is still maintained, CI/container parity passes, and dependency compatibility is verified. Upgrade supported major versions with dedicated matrix and release notes.


## Upstream compatibility read-through — 2026-11-23

This section records a read-only technical cross-check of upstream compatibility sources. It does **not** sign off the maintainer-owned review ledger: the pnpm, PostgreSQL, Playwright and Ubuntu-runner entries in `runtime-support-review.json` remain past their review-by dates until the accountable repository maintainer confirms and updates them.

- **Node.js:** Node 24 remains an LTS line and Node 26 is also LTS. The repository intentionally stays on Node 24 for the current candidate; do not switch major versions as part of stabilization without a separate native-addon and CI matrix. Source: [Node.js release schedule](https://nodejs.org/en/about/previous-releases).
- **pnpm:** pnpm 11 supports Node 24, and pnpm 12 is now the current release line. Keep the repository's explicit `11.17.0` pin for this stabilization candidate; evaluate pnpm 12 separately with a lockfile/toolchain migration rather than silently following `latest`. Source: [pnpm installation and compatibility](https://pnpm.io/installation).
- **PostgreSQL:** PostgreSQL 16 remains supported; the upstream policy lists 16.16 as the current minor and 2028-11-09 as the final release date. The repository currently selects the PostgreSQL 16 image line, so a minor refresh should be a controlled test-image update. Source: [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/).
- **Playwright:** its documented system requirements include Node 24 and Ubuntu 24.04, matching the pinned CI baseline. Source: [Playwright system requirements](https://playwright.dev/docs/intro).
- **GitHub Actions runner:** the `ubuntu-latest` label migration to Ubuntu 26.04 was scheduled to complete by 2026-11-19. Workflows should remain explicitly pinned to `ubuntu-24.04` until an intentional Ubuntu 26.04 canary passes; do not inherit a moving `latest` label. Source: [runner-images announcement #14748](https://github.com/actions/runner-images/issues/14748).

The latest code correction also makes `scripts/check-action-pins.mjs` inspect the Dockerfile for the exact pnpm pin, so a major-only Corepack declaration is now intended to fail the same drift gate as a mismatched workflow pin. Hosted verification for that correction is pending on the new exact `dev` head.
