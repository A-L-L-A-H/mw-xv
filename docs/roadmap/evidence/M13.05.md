## Architectural & Concurrency Boundaries (Handoff #7–#8)

- **Creation vs. Run-Start Boundary:** This gate protects **new WorkContract creation** at `POST /projects/tasks/:id/work-contract` and `POST /api/projects/tasks/:id/work-contract`. It does **not** enforce project DAG readiness on later `POST /ai/runs` execution-start endpoints (a separate execution boundary).
- **Transaction & Locking Residual Risk:** Readiness evaluation and `WorkContract` + `AcceptanceCriterion` insertion execute atomically inside one `ProjectTask.transaction(trx)` boundary (serializing SQLite writes and forwards `trx` to `isValidAiMutation`). However, generic dependency writers (`POST/PATCH /api/models/project.task_dependency`) do not take a `FOR UPDATE` row lock on the target `project_tasks` row; closing concurrent multi-writer PostgreSQL races requires explicit row-level locking on dependency writers in a bounded follow-up rather than claiming full race immunity here.
