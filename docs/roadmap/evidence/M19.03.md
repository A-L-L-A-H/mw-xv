# Evidence M19.03 — Make Rust ISP container build reproducible from a clean clone

## Status

- Complete on `feat-m19-03-reproducible-build` (based on `dev` at `a52319a5`), opened as a PR to `dev`. PR link recorded in the task issue; single commit referencing Task ID M19.03.
- Deliverable per the card: resolve issue #378 by committing the production `Cargo.lock` for `apps/isp` and making the Docker/Compose build match the actual SQLite edge runtime.

## Kontrak dan hasil

- Perilaku sebelum: `apps/isp/Cargo.lock` was git-ignored, so a clean clone could resolve different dependency versions (unreproducible build). `apps/isp/docker-compose.yml` still referenced the removed `apps/radius` service (nonexistent `apps/radius/Dockerfile`, nonexistent `./apps/radius/config.toml` mount, obsolete `MW_RADIUS_*` postgres env vars, and a PostgreSQL dependency the binary does not use).
- Perilaku sesudah / deliverable: `Cargo.lock` is tracked (generated with `cargo generate-lockfile` and validated by a full `cargo build --release`); `.gitignore` keeps `/target/` but no longer excludes the lockfile. `docker-compose.yml` now builds `apps/isp/Dockerfile` from the repo-root context, runs the SQLite edge runtime with a named volume for the database file, publishes RADIUS auth 1812/udp + accounting 1813/udp + HTTP admin 3000, and only sets env vars the binary actually reads (`MW_ISP_DB_PATH`, `MW_ISP_ADMIN_TOKEN`, `RUST_LOG`).
- File yang diubah: `apps/isp/.gitignore`, `apps/isp/Cargo.lock` (new, tracked), `apps/isp/docker-compose.yml` (rewritten), `scripts/isp-compose-config.test.mjs` (new verification test), root `package.json` (`test:isp` script), `docs/roadmap/20-isp-rust-go-architecture-aaa.md` (M19.03 acceptance checklist), this evidence file.
- Public API/schema/config yang terdampak: none in application code; `apps/isp/src/main.rs` untouched (in flight on PR #417).
- Keputusan dan alasan: compose uses `MW_ISP_ADMIN_TOKEN` with a local default only (`${MW_ISP_ADMIN_TOKEN:-local-admin-token}`); production deployments should instead provide `MW_INTERNAL_SECRET`/`JWT_SECRET` so the binary derives the bearer token via HMAC-SHA256, or leave all unset to persist a generated token beside the database. The env→Config mapping assertion in the test encodes the `config` crate prefix semantics (`MW_ISP_<FIELD>` → snake_case `Config` field) rather than a literal string match in `main.rs`.
