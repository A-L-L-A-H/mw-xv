# Unified Master Proposal — MoonWitness & Related Idea Ecosystem

**Proposal version:** 0.1 · **Prepared:** 2026-11-23 · **Target:** A-L-L-A-H/mw-xv  
**Classification:** `PROPOSAL` informed by `USER IDEA`, `REPOSITORY-DOCUMENTED` and current MW-XV architecture. It does not alter user canon, authorize legacy imports or approve all product ideas.

## 1. Unified vision

Build one navigable knowledge and product ecosystem that can preserve original ideas and source evidence, connect stories/research/products without erasing their identity, and turn only accepted work into bounded execution tasks.

The unifying principle is **source → interpretation → decision → experience**, with provenance and uncertainty retained at every step.

MoonWitness is the central message / witness / shared-experience product direction. Related creative work, ROCKSOUL frameworks, GOD PROMISE, Asmaul Husna research, Empire of the Light, ARSY and adjacent engineering experiments are associated workstreams—not automatically one narrative canon, one platform service or one brand surface.

## 4. Target architecture

### Platform layer
- One API/control plane in MW-XV.
- One Board surface for public/product experience and admin workflows.
- One canonical auth / tenant / permission authority.
- Addon manifests and one installer/registry lifecycle.
- PostgreSQL-backed durable records, audit, jobs and outbox.

### Knowledge layer
- Corpus: exact source identities, editions, passages, citations, rights.
- Research: analysis, comparison, extraction rules, hypotheses and counter-evidence.
- Knowledge: source-backed records, story/editorial review and publication.
- Ontology: typed identity and relationship contracts with evidence and human review.
- Assets: original artwork masters, variants, review status, rights/provenance.
- Documentation: raw → brain → accepted spec/ADR/knowledge record; not a second runtime database.

### Execution layer
- Desktop is a constrained local execution harness.
- AI Runtime and MCP integrations stay behind capability grants, risk gates, sandboxed worktrees and human approvals.
- Proof-carrying work: source SHA, diff, tests, verification and rollback evidence.
- TaskOS remains the task lifecycle source; GitHub Issues are its human-facing projection.

### Experience layer
- Public Board for approved content.
- Existing UI Catalog / Creative Lab for artwork review.
- Radio is initially a product specification, not a new data store until on-demand/scheduled/live requirements are decided.
- Community/progression/Extension Hub remain proposals in #15 until explicit acceptance and source-backed gap proof.

## 5. Proposed cross-project journey

```text
RAW IDEA / SOURCE
      ↓ provenance + classification
IDEA / PROJECT / STORY / RESEARCH RECORD
      ↓ link typed sources and uncertainty
HUMAN REVIEW / CANON / PRODUCT DECISION
      ↓ approved bounded work only
TASKOS → MANAGED ISSUE → LOCAL / CLOUD EXECUTION
      ↓ proof, tests, visual review, privacy/rights gate
DEV → REQUIRED CI → PROMOTION REVIEW → MAIN / RELEASE
      ↓ publication projection only where approved
BOARD / STORY / RADIO / CREATIVE EXPERIENCE
```

No automatic step can declare divine approval, canonical identity, external dispatch, product release or public publication without its relevant evidence and human gate.

## 7. Religious and philosophy boundaries

- Maintain work / witness / canon / edition identity as distinct.
- Keep translation, source language, tafsir, interpretation, personal reflection and metaphor separate.
- Treat numerical frameworks (1·6·3, 72→73, 9 Gates / 13 Ways, Q47:35 word patterns) as owner-originated hypotheses / editorial frameworks pending source verification, not accepted doctrine or scientific formulas.
- Treat HISTA, Four Pillars of Soul, AR-RUH Absurd Theory, nafs/physical/infrastructure and motivational formulas as personal frameworks/metaphors unless independently validated in an appropriate domain.
- No private testimony, account export or child-sensitive content is publicly stored or used by general-purpose AI without separate consent and safeguarding controls.

## 12. Alternatives considered

1. **Keep all source repos active and create a single link directory:** preserves identity but leaves duplicated ownership and scattered workflow.
2. **Bulk-migrate everything into MW-XV:** rejected under K0-006; violates rights/privacy and duplication constraints.
3. **Delete legacy repos after moving docs:** rejected until mirror, rights, dependency and restore evidence are complete.
4. **Create new app/ORM for every idea:** rejected; many domains are already owned in MW-XV or should remain documentation / story / research.
5. **Current proposal: source-preserving archive + selective clean-room requirements + existing MW-XV ownership:** recommended.
